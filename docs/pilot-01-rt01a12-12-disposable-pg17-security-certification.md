## Authorized resource and strict exclusions
The **only** database permitted is the fresh GitHub Actions `postgres:17-alpine` service with database `pilot01_disposable_rt01a12_12_ci`, user `postgres`, synthetic password and loopback host/port 127.0.0.1:5432. The test requires both `PILOT01_A12_12_DISPOSABLE_PG=I_ACKNOWLEDGE_NEW_EMPTY_PG17_ONLY` and the exact disposable URL, checks version 17, server identity, no existing public tables, no test roles and no non-system schemas **before executing any fixture DDL**. Failure exits without fixture modification. The test cannot access Railway, staging, Production, restored/customer or other existing databases.

No operational migration, runtime adapter/export, API route, worker, deployment, provider call, credential retrieval, or public-site write is permitted. `PUBLIC_SITE_WRITES_ENABLED=false` and `AI_PROPOSAL_GENERATION_ENABLED=false`. ## Certification design
1. On a newly attested empty disposable database, replay the ordered **canonical migrations 0001–0011**, each as its existing reviewed SQL source, then apply the **already existing** PILOT-01 SQL candidate only as a **test fixture**. The source files are not edited and are not installed into operational migration directories.
2. Add **test-only** tenant membership and issuer custody tables with scoped role, positive revision, expiry and revocation fields; add an immutable mapping of synthetic PostgreSQL role to tenant. These tables do **not** implement trusted production issuer signatures or owner issuance authority. SHA-256 provenance remains a fingerprint, not authentication proof.
3. Create two `NOLOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT` application probe roles. Test `ENABLE` + `FORCE ROW LEVEL SECURITY` and tenant policies on five candidate PILOT-01 tables and test-only custody/probe tables. Tenant policy derives scope from a DB-owned role-to-tenant mapping keyed by `current_user`, **not** from an arbitrary client-controlled tenant GUC. Privileged fixture setup remains separate from test-role assertions. In practice `SET LOCAL ROLE` impersonation is performed only by the disposable superuser harness and does **not** prove production principal authentication.
4. Use the existing candidate grant → job → immutable admission → event structures in one database transaction with lock-protected session/site/membership/issuer evidence and revision fences. A membership revoke before admission denies. Admission holding a membership share lock must finish before a competing revocation update can commit. Issuer revocation also denies; outdated revision rejects.
5. Verify tenant-isolated SELECT and INSERT, no cross-tenant leakage through sequential pooled role changes, idempotency replay/conflict, rollback when event insert fails, and a read-only post-commit receipt query. Outbox eligibility and external effects stay blocked. For an acknowledged commit whose receipt was withheld, a read-only query is a **simulation**; this test alone does not certify actual TCP-level COMMIT-loss handling. Existing RT01-A10 transport-wire tests provide separate isolated coverage.

## Important limitations / release blockers
- The policy and custody schema are **test-only proposals**. No operational membership persistence, issuer cryptographic verification, RLS role grants, application identity binding, connection-pool implementation or production transaction adapter exists from this milestone.
- Canonical replay is on a **fresh empty instance**. It cannot detect drift, existing owner grants, live index/lock cost, current production migration ledger/checksum, historical data compatibility, or rollback impacts in any existing database.
- The injected fixture identity is synthetic and `SET LOCAL ROLE` from a test superuser demonstrates PostgreSQL RLS enforcement under a restricted effective role, **not real authenticated login**. Public canonical tables and production session policy are not certified end-to-end.
- Every revocation writer in a future adapter must obey the same lock/version protocol as admission. A single controlled race test is not proof against all deadlocks, snapshot anomalies or process-fault conditions.
- Future work still requires independent threat modeling, reviewed least-privilege production grants and SECURITY DEFINER policy, trusted issuer signing/attestation, canonical integration and migration staging strategy, and separately authorized runtime rollout.
- A dedicated CI run is execution evidence for the isolated test suite only. Do not promote synthetic results to a production release claim.
