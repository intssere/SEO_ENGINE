## Decision proposal — **additive, dedicated pilot namespace** (not an approved DDL script)

Prefer a separately owned `pilot01` schema or rigorously namespaced pilot tables instead of retrofitting `public.jobs`. This avoids changing existing generic queue semantics, the specialized P8.8 mutation workflow, or current consumers. Names below are conceptual and **MUST NOT be executed** from this document.

| Proposed conceptual record | Required identity and invariants |
| --- | --- |
| `pilot01.grants` | UUID grant; canonical organization/site UUID; authenticated actor subject; server-owned issuer identifier and provenance; exact `analyze/recommend` operation; issued/expires/consumed/revoked timestamps; DB-clock state transition `issued→consumed OR revoked`; no site-write operation |
| `pilot01.jobs` | UUID job; strict grant/site/organization FK or composite integrity; actor and operation; pending/claimed/completed/failed/cancelled state; owner, **monotonic generation**, lease expiry, attempts, immutable admission linkage; no implicit dispatch when inserted |
| `pilot01.admissions` | immutable UUID receipt; unique grant and unique scoped idempotency key; unique job link; actor, org, site, issuer, operation, transaction ID, database-issued timestamp, receipt provenance; exact-scope replay only |
| `pilot01.job_events` | append-only job/claim/renew/complete/cancel event with owner generation and correlation to authorized admission; transition ID uniqueness |
| `pilot01.outbox` | separate read-only operation intents only; durable deduplication key and exact admission/job/owner/generation reference; dispatch policy verified **again** at delivery; stale generation cannot emit effects |
| `pilot01.issuers / membership binding` | undecided: prefer authoritative external identity and membership tables/ports with explicit custody over copying unauthenticated role strings; stable revocation behavior needs review |

### Key referential integrity proposal

- Use UUID organization/site FKs matching canonical tables. Enforce **same tenant/site pair**, not separate unrelated `organization_id` and `site_id` FKs. If necessary, review a composite unique key on canonical `sites(organization_id,id)` or equivalent server-authenticated trigger/transaction policy **without altering existing schema yet**.
- Avoid weakening `jobs.site_id` nullability or its existing state checks; old jobs remain the legacy path until an independently authorized cutover.
- Unique idempotency must be **scoped** to tenant, site and durable grant, with exact-request fingerprint and conflicting-key denial; decide whether global unique keys are additionally required. Never silently allow same key and different grant to be treated as a replay.
- Protect immutable admission/event receipts against UPDATE/DELETE with database role privileges and independently reviewed enforcement; unique constraints alone are insufficient for immutability.
- DB-clock TTL checks are under a locked transaction; do not use caller/system wall time to authorize grant expiry or lease renewal.
- Separate grant revocation (before consumption) from cancellation of an already running admitted job and its outbox. Define both race semantics.
- Preserve tenant isolation through least-privilege roles and an explicit RLS design (including background worker bypass/owner semantics). No user-controlled session variable constitutes identity by itself.
- For effects outside one transaction, exactly-once external execution is **not** implied by exactly-once admission; provider-specific idempotency/ack and outcome-unknown recovery require their own certification.

## Migration sequence proposal — future separate authorization required

**M0. Provenance gate (read-only proposal, not performed):** operator-approved inventory of database resource identity, current migration ledger, applied checksums, actual schema, UGP/CVI ownership, permissions, runtime image digest and rollback capability. Stop on any drift or unknown owner.

**M1. Design review:** settle tenant/site composite integrity, subject-to-organization membership model, issuer custody, state machine, privileges/RLS, retention and outbox policy; independent Tahseen + security review and owner approval of exact migration diff.

**M2. Additive non-production schema rollout:** only after distinct authorization, apply a versioned forward migration on separately approved isolated DB with explicit rollback and synthetic fixtures. No modifying `public.jobs`, `auth_sessions`, or `policy_mutation_dispatches` without a specific compatibility decision.

**M3. Synthetic certification:** isolated DB tests for atomic admission + audit, concurrent/revoked/expired grants, cross-tenant and issuer forgery, unique receipts, lost COMMIT ack, crash/reconcile, lease takeover, fenced stale worker/outbox. Verify role privileges and negative RLS tests against the proposed real schema.

**M4. Runtime adapter and cutover (separate milestone):** bridge enforced real principal, membership, issuer custody and approved admission to the new namespace. Maintain default-deny and no provider dispatch on receipt ambiguity. Do not enable a worker on migration alone.

**M5. Release readiness:** distinct operator approval for each environment migration, deployment/image and DB binding, bounded provider reads, explicit feature gates and rollback rehearsal.

## Rollback and no-downgrade principles

- No automatic switch back to the legacy `pilot_ingestion_v1` queue on errors. Disabled integration must remain disabled.
- If additive schema tables are empty/unreferenced, rollback can be considered only after ledger/ownership validation. Once durable receipts, leases or outbox records exist, destructive down-migrations are unsafe; prefer freeze, quarantine and forward repair with explicit retention.
- Preserve existing UGP `0001–0011` migrations and existing row semantics; any changes require independent impact analysis.
- Never infer successful application of a migration from a merged PR, passing CI or documentary claim.
